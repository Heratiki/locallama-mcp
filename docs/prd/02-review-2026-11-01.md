**BLOCKERS**

1. **§§5.2, 11 — The assumed PRD 01 integration is absent from this checkout.** `src/index.ts:LocalLamaMcpServer.run` calls only route recovery; `tool-definition/index.ts:getAvailableTools` has no `patch_task`; `PatchWorker` has no production caller. `job-store/recovery.ts:recoverInProgressJobs` explicitly skips patch Jobs. **Fix:** identify the prerequisite revision containing PRD 01’s dispatcher/tool integration and seed fixtures, and make it an explicit dependency before filing PRD 02 build issues.

2. **§6.2 — The quota contract cannot enforce its advertised limits.** `LLMProvider.hasRateLimitBudget()` takes no model or token arguments, while `QuotaTracker.hasBudget` requires both. Separate `hasBudget`/`reserve` calls provide no atomic admission result or reservation identity for reconciliation after errors, cancellation, or restart; aggregate `window_start/count` rows also cannot reconstruct an exact sliding window. **Fix:** specify durable, atomic reservations with model/window scope, token estimation, reconciliation, and conservative treatment of interrupted calls, including concurrent MCP server processes.

3. **§§5.2, 6.5; §12 Q3 — Waiting has no complete state machine or consistent clock.** `patch/worker/index.ts:PatchWorker.runJob` permanently advances past unavailable entries and counts a dispatched 429 as an attempt. `ladder/policy.ts:computeDeadline` uses `max_minutes` as the same deadline Q3-A proposes pausing, contradicting “`max_minutes` still limits the task.” Sleeping also occupies the sole patch worker and retains its search/workspace resources. **Fix:** define temporary quota skips versus exhausted entries, 429 accounting, wake selection, worker release, and durable deadline accounting across restart. Q3 needs independently specified ordering, clock, and wait-cap choices; its recommendation is currently internally inconsistent.

4. **§§4, 6.3 — Breaker ownership is described incorrectly.** `core/provider/registry.ts:executeWithConcurrencyLimit` neither checks the breaker nor records call failures. The route executor’s `task-execution/index.ts:executeWithProvider` records failures unconditionally; the patch model path does neither. Consequently, the proposed registry-only bypass cannot preserve the claimed behavior across callers. **Fix:** name one owner for breaker admission and outcome recording, remove duplicate caller accounting where necessary, and carry typed quota/authentication errors through OpenRouter’s existing string-error conversion.

5. **§§4, 6.1; §12 Q10 — The ranking diagnosis is false, and the recommendation is incomplete.** `patch/ladder/build.ts:buildLadder` ranks local and free candidates separately before concatenation: an unscored free model does not compete with local scores. `rank` also deduplicates by `model_id` alone, losing alternative providers serving the same model. **Fix:** correct the premise and specify provider/model identity, per-provider selection, the final global cap, and tie-breaking. Q10-A does not guarantee every provider survives the merge unless those rules change; its options omit that distinction.

6. **§§5.3, 7.1–7.4; §12 Q6 — Profile bootstrapping and measurement are undefined.** `config/index.ts:config` is constructed synchronously at import, and `buildConfigFromEnv` already assigns `LOCALLAMA_PROFILE` the meanings `default`/`lightweight`. Detection now needs runtime probes, while profile defaults supposedly depend on measurements made afterward. Moreover, `llama-cpp/index.ts:callApi` is nonstreaming and `LlamaCppProvider.executeTask` discards usage, so the proposed interface cannot measure first-token latency or actual token throughput. **Fix:** define bootstrap defaults, initialization order, existing-profile compatibility, measurement interfaces, and calibration persistence/fallbacks. Q6 includes the fixed-values alternative, but its recommended calibration option lacks these necessary contracts.

7. **§§7.2, 7.4, 10; §12 Q7 — The floor profile cannot currently guarantee availability or one resident model.** `PATCH_LOCAL_MODELS=1` limits ladder entries, not runtime residency; `LlamaCppProvider.releaseResources` is a no-op. `llamaCppModule._runHealthProbe` uses a separate short timeout and treats thinking output as degraded, while `LlamaCppProvider.isAvailable` requires healthy status—potentially excluding a slow reasoning model before the patient worker runs. **Fix:** specify floor health-probe behavior and runtime residency controls, then verify memory across inference, indexing, and checks together. Q7’s runtime alternatives are complete and its llama.cpp recommendation matches the code, but require these explicit support changes.

8. **§11 — The issue ownership and dependency graph is not buildable as written.** Issues 6 (`hardware/**`) and 7 (`hardware/pull/**`) overlap in wave 2. No issue owns changes to the main worker, `PatchState`, or `OpenRouterProvider`, although waiting and window migration require them; migrations also need an initialization hook in `job-store/db.ts:initJobStore`. Issue 10’s MCP doctor read overlaps issue 9’s tool/bootstrap files. **Fix:** assign every integration edit and shared file one owner, narrow the hardware globs, and put provider/registry integration after the tracker contract and implementation it consumes.

9. **§§6.1–6.2; §12 Q1, Q9 — First-wave descriptors require facts R1 does not supply.** R1 Part 1 gives no Cloudflare compatible base URL, explicitly leaves SambaNova’s base URL unconfirmed, and does not establish every provider’s day-reset semantics. Nevertheless, the descriptor requires `baseUrl` and either a timezone reset or rolling window. **Fix:** add a targeted R1 research prerequisite and an explicit unknown-reset representation; builders must not invent these values. Q1’s rollout options omit no obvious alternative, but the recommended wave lacks required grounding; Q9’s static-file recommendation is compatible, provided unknown facts remain representable.

**FOLLOW-UPS**

10. **§§7.2–7.4, 10; §12 Q4 — Small-context repair behavior needs verification.** `patch/prompt/builder.ts:buildPrompt` fills hinted files before repair errors, so reducing context can remove the feedback weak models need. `codeSearch.ts:readCodeFiles` retains whole files plus chunks without a memory ceiling. **Fix:** test a failed-then-repaired request under the floor profile and bound retrieval memory. Q4’s recommended Granite facts match R1 and no candidate option is clearly missing, but Q4-C’s cross-model score comparison conflicts with R1’s explicit warning that harnesses/settings differ.

11. **§§6.4, 7.4; §12 Q2 — Acknowledgement coverage and warning wording need tightening.** Consent is enforced only at ladder admission, whereas `src/index.ts:LocalLamaMcpServer.run` seeds registered providers into the shared model registry, and `OutputValidator.validate` can call a provider directly. “Unconfirmed” also does not establish that a provider reviews prompts. **Fix:** test acknowledgement enforcement at dispatch and doctor probes, and distinguish unknown terms from confirmed training/review terms. Q2’s options are complete and its recommendation is compatible with the research.

12. **§§7.3–7.5; §12 Q5, Q8 — Installation and download manifests lack required details.** `package.json:bin` exposes only `locallama-mcp`; its packaged files exclude `src/config`, and `scripts/copy-assets.js` copies only the lock helper. Profiles record rounded sizes but no digest or pinned revision despite mandatory hash verification. **Fix:** assign CLI/package asset changes and record exact byte lengths, digest, revision, destination, and interrupted-download behavior. Q5 and Q8 omit no necessary policy option and their recommendations are compatible; those implementation details remain required.
